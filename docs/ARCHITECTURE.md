# Architecture

Text Deboss Studio is a fully client-rendered canvas application wrapped in a server-rendered Next.js shell. There is no backend: no API routes, no database, no server state. The server's only jobs are delivering the static shell, SEO surfaces, and security headers.

## Layering

```
┌──────────────────────────────────────────────────────────┐
│ middleware.ts - per-request CSP nonce         [edge]      │
├──────────────────────────────────────────────────────────┤
│ app/ (App Router)                                        │
│   layout.tsx  - metadata, fonts, JSON-LD   [server, async]│
│   page.tsx    - shell: Header + Studio     [server]      │
│   robots.ts / sitemap.ts / manifest.ts     [build-time]  │
├──────────────────────────────────────────────────────────┤
│ components/studio/            [client, presentational]   │
│   Studio → ControlPanel + PreviewStage                   │
│   No state of their own; everything arrives via `studio` │
├──────────────────────────────────────────────────────────┤
│ hooks/useDebossStudio.ts      [client, stateful]         │
│   DebossState + activePreset + hint + isCopying          │
│   rAF render loop · font loading · ResizeObserver        │
│   downloadPng() · copyImage()                            │
├──────────────────────────────────────────────────────────┤
│ lib/deboss/engine.ts          [client-only, pure]        │
│   computeBlockLayout/buildBlockMask (per text block)  ·  │
│   computeLayout/drawScene (scene: all blocks + branding) │
│   ensureFont · buildExportCanvas · canvasToPngBlob        │
│ lib/deboss/constants.ts       [isomorphic data]          │
│ types/deboss.ts               [types only]               │
└──────────────────────────────────────────────────────────┘
```

Dependency direction is strictly downward. The engine never imports React; components never import the engine directly (they go through the hook).

## Rendering pipeline

1. **State change** (slider, a text block's content/font/position, preset, swatch, transparency) → `setState` in the hook.
2. An effect calls `scheduleRender()`, which cancels any pending frame and books a new `requestAnimationFrame`, so a burst of slider events costs exactly one paint.
3. `renderPreview()` measures the stage's inner width, calls `computeLayout(state, logicalW)` — a **scene**-level function that sizes the canvas (auto-aspect sizes from `state.textBlocks[0]` alone, see "Multiple text blocks" below) and then computes each block's own `Layout` (direction-aware word wrap + height clamp; direction is auto-detected per block, per `lib/deboss/direction.ts`) via `computeBlockLayout`, returning a `SceneLayout` — then `drawScene()` at `min(devicePixelRatio, 2)`.
4. `drawScene()` composites, per text block in `layout.blocks`: paper is drawn once (colour + cached noise tile + directional light gradient), then for each block in turn: glyph mask (`buildBlockMask`) → recess floor → dark inner shadow (top-left walls) → white inner highlight (bottom-right walls), all reusing the document's shared depth/shadow/highlight/blur/texture/tint/shadowColor. The branding watermark draws once, last, after every block. See the engine skill file for the inner-shadow compositing trick.
5. The canvas backing store is physical pixels; CSS `width/height` present it at logical size for crispness.

**Export** reuses steps 3-4 with `EXPORT_SCALE = 3` on an offscreen canvas, then `toBlob('image/png')` → object-URL download or `ClipboardItem` copy. This guarantees the PNG is pixel-identical (×3) to the preview.

## Why fonts load via Google Fonts `<link>` instead of `next/font`

`next/font` rewrites family names to hashed private names. The canvas engine must address faces by real family name in `ctx.font` and `document.fonts.load()` for correct shaping across scripts, so the app keeps the real families (the full list is in `FontFamily`, `types/deboss.ts`, currently twelve Google Fonts plus two self-hosted, plus UI-only "Inter") and the CSP allowlists exactly the two Google Fonts origins (`middleware.ts`) plus `'self'` for the self-hosted files. First paint of the canvas waits on `document.fonts.ready` plus explicit `fonts.load()` calls per family.

## Direction detection (RTL vs LTR)

`lib/deboss/direction.ts` exports `detectTextDirection(text)`, a first-strong-character scan run **per text block**, over that block's own `text` field. Both the engine (`ctx.direction` in `layoutLines`/`buildBlockMask`, and the rich-text measurement DOM below) and the UI (`dir` on `RichTextEditor.tsx`'s root, for whichever block is currently being edited) call it; there is no manual toggle and no hardcoded direction anywhere. Since a block's `text` may contain rich-text markup, every call site runs it through `stripTags()` (`lib/deboss/richtext.ts`) first: tag names/attributes are Latin characters that would otherwise misdetect LTR on genuinely RTL content. Because direction is resolved independently per block, one canvas can freely mix an Urdu/Arabic (RTL) block with a Latin/Devanagari (LTR) block, each shaping and wrapping correctly on its own.

## Rich-text formatting (bold/italic/underline/per-selection size)

`TextBlock.text` (`types/deboss.ts`) stays a plain `string`, now optionally containing a small, fixed, closed tag vocabulary (`<b>`, `<i>`, `<u>`, `<span style="font-size:Npx">`) that only `lib/deboss/richtext.ts`'s serializer ever generates. `RichTextEditor.tsx` (a full WYSIWYG editor built on Tiptap, loaded via `next/dynamic({ ssr: false })` to keep its bytes off the tracked First Load JS) mounts per block, only while that block is being edited; its toolbar drives Bold/Italic/Underline toggles and a pill-shaped size stepper (-/editable-input/+), gated per font by `FONT_CAPABILITIES` (`constants.ts`) so a font with no real bold/italic face never renders a browser-synthesized ("faux") style.

`engine.ts` has two layout paths per block, gated on `hasRichRuns(block.text)`. Untagged text stays on the original scalar path (`layoutLines`, one `fillText` per line, unchanged since before this feature) so every existing `GALLERY_EXAMPLES` entry and the default text render byte-identically to before. Tagged text goes through `measureRichLines`: canvas has no native mixed-run text layout API, and hand-rolling a bidi-aware line-breaking algorithm to replace the single-`fillText`-per-line approach (which gets correct Arabic/Urdu shaping "for free" from one call covering a whole line) risks exactly the kind of subtle RTL regression this project treats as a hard rule. Instead, `measureRichLines` renders the same tagged markup into a hidden, singleton DOM container (same lazy-create-and-reuse pattern as `_measureCtx`/`_noiseTile`) and reads back the browser's own bidi-correct, wrap-correct visual positions via `getBoundingClientRect` for each fragment's x/width, then `buildBlockMask` replicates those exact positions with one `fillText` call per word/sub-word fragment, drawing underlines as manually-filled rectangles into the same mask (so they inherit the shared recess/tint/shadow/highlight compositing for free).

Grouping fragments into visual LINES is done per paragraph via `Range.getClientRects()` over that paragraph's own content, not by comparing individual fragments' bounding rects to each other: a single inline fragment's own rect spans its full font ascent/descent, and a much larger font on one line can make that box tall enough to spatially reach into a neighbouring line's rect even though the two render on genuinely separate, non-overlapping CSS line boxes (this shipped as a real bug once: two same-paragraph or adjacent-paragraph lines with a big enough size difference rendered on top of each other). `Range.getClientRects()` on a whole paragraph returns the browser's own actual line-box rects, one per rendered line, which are guaranteed not to overlap; each fragment is assigned to whichever of its own paragraph's line-rects its vertical centre falls in.

One limitation the DOM bridge cannot fix: a style boundary landing mid-word still visibly breaks Arabic/Urdu letter-joining, since each `fillText` call shapes its substring in isolation regardless of how correctly it's positioned. `RichTextEditor.tsx` mitigates this by snapping a partial-word selection out to the nearest whitespace before applying any mark, for fonts in `CURSIVE_SCRIPT_FONTS` (`constants.ts`).

## Multiple text blocks (Canva-style layers)

`DebossState.textBlocks: TextBlock[]` (`types/deboss.ts`) replaces the old single `text`/`font`/`align`/`fontSize`/`letterSpacing`/`lineHeightFactor`/`textAnchorX`/`textAnchorY` fields on `DebossState` with an array; every other field (paper, engraving, tint, aspect, transparency, branding) stays shared/document-level across all blocks, since those are properties of the paper/lighting, not of any one piece of text. Each `TextBlock` carries a stable `id`, its own `text`, and its own full style (`font`, `align`, `fontSize`, `letterSpacing`, `lineHeightFactor`, `textAnchorX/Y`). `DEFAULT_STATE.textBlocks` is a single block (`DEFAULT_TEXT_BLOCK`, `constants.ts`) at the fixed id `"default"` and anchor `(0.5, 0.5)`, which is why a fresh/legacy single-text document renders byte-identical to before this feature existed: with exactly one block at the default anchor, every formula below reduces to what it computed pre-multi-block.

**Engine split**: `engine.ts` has a **block-scoped** layer, doing exactly what the old single-text functions did but parameterized on one `TextBlock` instead of the whole `DebossState` — `computeBlockLayout(block, maxWidth, logicalW, logicalH)`, `buildBlockMask(block, pxW, pxH, s, layout)`, `measureBlockBox(block, layout)` — and a **scene** layer that orchestrates all blocks against one shared canvas: `computeLayout(state, logicalW): SceneLayout` sizes the canvas (auto-aspect uses `state.textBlocks[0]` alone — deliberately not a bounding box of every block, which would be circular, since canvas size would depend on block positions that are themselves fractions of canvas size) then computes each block's own `Layout` against those final dimensions; `drawScene(target, state, layout, s, transparent, suppressBlockId?)` loops `layout.blocks`, running the shared recess/tint/shadow/highlight steps once per block's own mask, skipping only the one block matching `suppressBlockId` (see below), then draws the branding watermark once, last, unconditionally. `buildExportCanvas`, `MiniPreview.tsx`, and `GalleryPreview.tsx` never pass `suppressBlockId`, so exports and read-only previews are unaffected by live editing state, the same parity guarantee `drawScene` has always given preview vs. export.

## In-canvas text editing & free positioning

There is no sidebar text box. `CanvasTextOverlay.tsx` (rendered inside `PreviewStage.tsx`'s `.stage-inner`) renders one `BlockOverlay` per entry in `state.textBlocks`, each reusing `RichTextEditor.tsx` as a true in-place overlay for that one block, absolutely positioned and sized to match the canvas rendering exactly, rather than a fixed-size box with its own decorative styling. This works because `RichTextEditor.tsx`'s DOM-styling effect sets font-family/size/line-height/letter-spacing/text-align/dir imperatively from that block's own fields (the same values `buildBlockMask` reads), instead of a fixed CSS approximation.

Each block cycles through three states, disambiguated by pointer movement rather than a separate "select" click: **idle** (invisible hit-region, `.canvas-text-hit`), **selected** (same hit-region plus a persistent outline and a small delete `×` button, `.is-selected`), and **editing** (mounts `RichTextEditor` inside `.canvas-text-overlay`; a floating formatting toolbar appears only while text is selected within it, anchored to the selection and portaled to `document.body` rather than nested there, so it's never clipped by `.stage-inner`'s `overflow: hidden` near a canvas edge, see the gotchas file for the selection-tracking, positioning, and touch-handling details). A plain click on an idle/selected block's hit-region selects **and** edits it in one step; a press-and-drag past a small threshold (`DRAG_THRESHOLD_PX`) instead selects and repositions it via `setBlockPosition`, without entering edit mode. Below every per-block hit-region, a full-canvas `.canvas-text-background` catch-all layer (lowest in paint order, so per-block elements always receive pointer events first) turns a plain click on genuinely empty canvas into `addTextBlock(x, y)`, which appends a new block (copying the currently-selected block's style, or block `[0]`'s if none is selected, capped at `MAX_TEXT_BLOCKS`) and immediately selects + edits it; that background layer tracks whether a block was already being edited at `pointerdown` time (`wasEditing`, captured before the child's own outside-pointerdown-dismiss listener can clear it) so the same click that only dismissed an open editor doesn't also spawn a new block. `RichTextEditor` is loaded via `next/dynamic` from `CanvasTextOverlay.tsx` itself and only mounted for whichever block is actively being edited, so its bytes aren't fetched until the first click.

**Delete**: the Delete/Backspace key (while a block is selected-but-not-editing) and the small `×` button both call `deleteTextBlock(id)`, which clears `selectedBlockId`/`editingBlockId` if either pointed at the removed block. The delete button's `onPointerDown` **and** `onPointerUp` both call `e.stopPropagation()` — stopping only `onPointerDown` was a real bug caught during verification: with only `pointerdown` stopped, the button's `pointerup` still bubbled to the parent hit-region's own `onPointerUp` handler, which (seeing no drag in progress) fired `setEditingBlockId(id)` for the very block about to be deleted; that re-render swapped the button out of the DOM for the edit container before the browser's synthesized `click` event could ever land on it, so `deleteTextBlock` silently never fired and the block survived, stuck in edit mode. Any future control nested inside a `.canvas-text-hit` that needs to intercept a gesture must stop propagation on `pointerdown`, `pointerup`, **and** `pointercancel` together, not just `pointerdown`.

While a block is being edited, the canvas itself stops drawing that ONE block's debossed render, so the flat overlay is the only visible copy of it — every other block, plus paper and the branding watermark, keep drawing normally underneath. `editingBlockId` lives in `useDebossStudio.ts` (not local to `PreviewStage`/`CanvasTextOverlay`), since the render loop needs it: `renderPreview` passes it to `drawScene` as `suppressBlockId`. `buildExportCanvas` never passes it, so the committed/exported result is unaffected by live editing state.

Two boxes are computed per block per render (`computeContentBox`/`computeEditBox` in `CanvasTextOverlay.tsx`, both built on `measureBlockBox` from `engine.ts`): the **edit** box always spans the engine's own wrap width (`logicalW - 2*PAD_X`) so typing/wrapping matches the canvas regardless of where the block has been dragged, while the **content** box hugs that block's actual measured text (used for the idle/selected hit-region and for drag clamping) so short or centered text gets real room to move instead of being confined to the wrap column.

Position itself (`TextBlock.textAnchorX/Y`, normalized 0-1, default `(0.5, 0.5)` per block) is a single **additive offset** applied on top of whatever `align`-based position `buildBlockMask` would already compute — `dx = (textAnchorX - 0.5) * logicalW`, `dy = (textAnchorY - 0.5) * logicalH` — not a redefinition of alignment or wrap width. At the default this is a no-op, so a single-block document at its default anchor renders unchanged; dragging just shifts that one block, alignment/wrapping logic never needs to know positioning exists. The same principle already established for the branding watermark (`brandingX/Y`) applies here: position excluded from `CustomSet`/`toSetSnapshot` (a `CustomSet` excludes `textBlocks` entirely — see below), not persisted to `localStorage` (unlike branding *text*, which is; block position is per-document like block text itself).

A known, disclosed limitation: DOM (contentEditable) and Canvas 2D (`fillText`) text metrics aren't always pixel-identical, most visibly when the active font doesn't cover the typed script (e.g. Latin text with a Nastaliq font selected causes the two fallback chains to resolve to different substituted fonts). This is the same category of trade-off `measureRichLines`' DOM-measurement bridge already accepts; not chased further.

**Type & Paper section's Font select targets a block**: `ControlPanel.tsx`'s font select reads from and writes to `state.textBlocks.find(b => b.id === selectedBlockId) ?? state.textBlocks[0]` via `setBlockFont`, not a top-level field — it prefers the selected block, but falls back to the first block rather than disabling itself when nothing is selected, so it's always usable. (Alignment and the letter-spacing/line-height sliders, `TYPE_SLIDER_DEFS`/`TextBlockSliderId` in `types/deboss.ts`, previously lived here too, gated on selection with a disabled/hint state when nothing was selected; both were removed from this section at the user's request to declutter it, though the underlying `TextBlock` fields and their use in `engine.ts` are unchanged.) Aspect, tint/shadow colour, paper tone, and branding stay global/document-level fields in the same section, unaffected by selection.

## State model

`DebossState` (in `types/deboss.ts`) is the single source of truth for a render. It is mirrored into `stateRef` so the rAF callback and export handlers always see current values without re-subscribing. UI-only state (`activePreset`, `activeCustomSet`, `hint`, `hintFlash`, `isCopying`) lives beside it in the hook but never enters the engine.

Preset semantics: applying a preset overwrites the five engraving parameters + paper tone and marks the preset chip active; any manual slider/swatch change clears the active chip (the values remain).

**Deep links**: `page.tsx` awaits `searchParams`, validates a `?preset=<id>` value against `PRESETS`, and passes the result down as `Studio`'s `initialPresetId` prop; `useDebossStudio.ts` applies it in a mount effect declared after the custom-sets/default-set load effect, so a shared link wins over a starred default. `page.tsx` also exports a `generateMetadata` that returns a per-preset title/description/canonical for that same value. Picking a preset client-side afterward calls `router.replace` to keep the URL in sync (`setPresetInUrl`); the same mutators that already clear `activePreset` (slider, paper swatch, applying a Set) also strip the query param (`clearDeepLinkFromUrl`).

**Gallery examples** (`GalleryExample` in `types/deboss.ts`, `GALLERY_EXAMPLES` in `lib/deboss/constants.ts`) extend the same deep-link mechanism to a `?example=<slug>` param, resolved in `page.tsx` the same way, and applied in a THIRD mount effect in `useDebossStudio.ts`, declared after the preset effect so an example wins if a URL somehow carries both. Unlike a preset (5 engraving fields + paper only) or a `CustomSet` (everything except text), a `GalleryExample` is the full `DebossState` including text, since a gallery example's whole point is one specific text+look pairing. That widens which mutators must clear it: every mutator that already clears `activeCustomSet` also clears `activeExample` and strips `?example=` (`clearExampleFromUrl`, which removes only that param, leaving `?preset=` untouched, since presets don't share the same invalidation rules), PLUS every per-block mutator (`updateTextBlock`, `setBlockFont`, `setBlockPosition`, `addTextBlock`) via a shared `invalidateExample()` helper, since editing/moving/adding a block breaks the one thing a `GalleryExample` uniquely pins (its exact `textBlocks`). `setBlockPosition` and `deleteTextBlock` are the exceptions, matching branding's precedent: position is orthogonal to "the look," and deleting a block that a Set/preset never referenced in the first place doesn't invalidate either. `components/studio/GalleryPreview.tsx` (modeled on `MiniPreview.tsx`, but full multi-line layout instead of a single-glyph swatch) renders each example with the real engine on its own `/gallery/[slug]` page, a new, independent read-only display context outside the preview/export parity rule.

## Custom sets (client-side persistence)

`CustomSet` (`types/deboss.ts`) is a user-named snapshot of `DebossState` minus `textBlocks` and branding: aspect, engraving, paper, tint, shadow colour. Font/alignment/letter-spacing/line-height moved onto each `TextBlock` when multi-block support landed, so a Set (one saved look) can no longer sensibly carry them, a single Set can't map onto N independently-styled blocks; applying a Set now only ever restores document-level fields, never touches `textBlocks`. Unlike `Preset`s (built-in, four fixed configurations, engraving+paper only), sets are created by the user and cover the whole *shared* look.

They're the app's only persisted data, stored as JSON in `localStorage` under `CUSTOM_SETS_STORAGE_KEY`; still no server, no cookies, no network write. `useDebossStudio.ts` loads them once on mount and re-persists on every change, guarded by a `customSetsLoadedRef` so the pre-load empty array can't clobber storage before the initial read resolves. Every `localStorage` call is wrapped in `try/catch` since it can throw (private browsing, quota, disabled storage); a set then just lives for the current session instead of failing the app.

**Default set**: one set's id can be stored separately under `DEFAULT_SET_STORAGE_KEY` (`defaultSetId` state, toggled via `toggleDefaultSet`). The load effect that reads `customSets` also looks up this id and, if it still matches a saved set, applies that set's `state` to `DebossState` *in the same effect*, not a later one, so the change lands before the font-loading promise resolves and the first real canvas paint happens (`renderPreview` is gated on `fontsReadyRef`, which is far slower than a synchronous `localStorage.getItem`). That ordering is what avoids a visible flash of the built-in default before the user's default appears. `deleteCustomSet` clears `defaultSetId` if the deleted set was the default.

## Server vs client boundary

`page.tsx` and `Header` are server components; the header, landmarks, and metadata are in the HTML for crawlers. `Studio` is the single `"use client"` island; hydration cost is limited to it (First Load JS ≈ 107 kB total).

## CSP nonce + why the root route isn't static

`middleware.ts` runs on every request, generates a random nonce, and sets it as both the `x-nonce` request header and the response's `Content-Security-Policy` header (see `docs/SECURITY.md` for the full rationale: Next's App Router needs a nonced/trusted `script-src` for its own scripts, and a static `script-src 'self'` blocks them entirely in production). `layout.tsx` calls `headers()`; reading a Dynamic API is what makes Next render this route per-request rather than serving a cached static shell, which is the only way its renderer can see this request's nonce and stamp it onto the scripts it manages. Skip that call and every script gets blocked (we hit this once already). The nonce value itself is **not** applied to the one inline script the app authors (the JSON-LD block): it's `type="application/ld+json"`, which browsers never enforce `script-src` against (inert data, not executed), and nonce'ing it caused a hydration mismatch (browsers strip a script's `nonce` attribute from the DOM right after insertion). Net effect: `layout.tsx` is `async` and the root route renders dynamically (`ƒ` in the build output) instead of being statically prerendered; an accepted, required trade-off, and there's no expensive data fetching on this route, so the cost is negligible.

## Offline PWA (public/sw.js)

`public/sw.js` is a hand-rolled service worker (no `next-pwa`/`serwist` dependency): network-first for navigations (falls back to the cached shell offline), cache-first for same-origin hashed assets, stale-while-revalidate for cross-origin Google Fonts requests. Since this app has no backend and no data fetching, everything runs off client-side canvas + `localStorage`, so once the shell is cached the whole studio keeps working with no connection at all.

`src/components/layout/ServiceWorkerRegister.tsx` registers it, gated to `NODE_ENV === "production"` only; registering it in dev would let its cache-first strategy serve stale JS chunks over Fast Refresh's freshly rebuilt ones. The manifest (`app/manifest.ts`) lists SVG, PNG (192/512), and maskable (512, `purpose: "maskable"`) icons; `layout.tsx`'s `appleWebApp` metadata plus an `apple-touch-icon.png` cover iOS's separate "Add to Home Screen" icon convention. See `docs/SECURITY.md` for the CSP's `worker-src 'self'` and the service worker's (minimal) threat-model impact.

## Build & quality gates

`npm run build` runs ESLint (`next/core-web-vitals` + TS rules) and strict type-checking (`strict`, `noUncheckedIndexedAccess`). The root route (`/`) renders dynamically because of the CSP nonce (see above); `robots.txt`, `sitemap.xml`, and `manifest.webmanifest` remain statically generated since they're separate route handlers outside the React tree.
