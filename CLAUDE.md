# CLAUDE.md: Text Deboss Studio

This file orients Claude Code (and any AI coding agent) working in this repository. Read it fully before making changes.

## What this project is

A single-page Next.js 15 (App Router, TypeScript, React 19) web app that renders any text (Urdu, Arabic, Hindi, English, and more) as a **debossed / blind-letterpress effect** on textured paper using the HTML5 Canvas 2D API, and exports it as a high-resolution PNG. There is **no backend, no server database, no auth, no API routes**; all rendering happens in the user's browser. User-saved "sets" (see below) persist client-side in `localStorage` only; nothing is ever sent to a server. The default sample text is Urdu (`یہاں لکھیں`), reflecting the app's origin, but the engine and UI are script-agnostic.

It was ported 1:1 from a vanilla HTML/CSS/JS app. Feature parity with the original is documented in `docs/FEATURES.md`; do not remove or regress any feature listed there.

npm run dev        # dev server

## Architecture in one paragraph

`src/lib/deboss/engine.ts` is a **framework-agnostic, client-only** canvas engine: pure functions that take a `DebossState` and draw onto a canvas (glyph mask → inner shadows → composite onto paper). `src/hooks/useDebossStudio.ts` is the **only** place interactive state lives; it owns the rAF-coalesced render loop, font loading, ResizeObserver, and export/copy actions. Components under `src/components/studio/` are presentational and receive everything via the `studio` object. Full details: `docs/ARCHITECTURE.md` and `.claude/skills/text-deboss-engine/SKILL.md`.

## Hard rules (do not violate)

1. **Preview/export parity.** Preview and PNG export MUST share the same `drawScene()` path. Never add a preview-only or export-only visual tweak.
2. **The engine stays framework-free.** No React imports in `src/lib/deboss/`. It touches `document` only lazily (functions, not module top-level side effects), so importing it during SSR stays safe.
3. **Security headers stay strict.** The Content-Security-Policy lives in `src/middleware.ts` (nonce-based `script-src`, generated per-request; NOT a static header in `next.config.mjs`; see the comment in `middleware.ts` for why). It allowlists only self + Google Fonts, plus `worker-src 'self'` for the offline service worker. If you add an external resource, you must update the CSP deliberately and document why in `docs/SECURITY.md`. Never widen `script-src` in production. Never re-add a `Content-Security-Policy` entry to `next.config.mjs`'s `headers()`: a second CSP header there combines with middleware's via intersection and silently blocks Next's own hydration scripts again (this shipped broken to production once already). Never re-enable `poweredByHeader`.
4. **No secrets in `NEXT_PUBLIC_*`**: those are shipped to the browser.
5. **Direction is auto-detected per text block, not hardcoded.** `src/lib/deboss/direction.ts` (`detectTextDirection`) picks `"rtl"` or `"ltr"` from the first strong-directional character in a `TextBlock`'s own `text`. Both `ctx.direction` in the engine (`layoutLines`, `buildBlockMask`, and the rich-text measurement DOM) and `dir` on `RichTextEditor.tsx`'s root (for whichever block is being edited) MUST derive from this function, called separately per block; never hardcode `"rtl"` or `"ltr"` again, that would regress either script, and never assume one direction applies to every block on the canvas. Because a block's `text` may contain rich-text markup (see below), always run `stripTags()` (`lib/deboss/richtext.ts`) on it first: tag names like `span`/`style` are Latin characters that would otherwise misdetect LTR on genuinely RTL content. Font family names in `types/deboss.ts` must exactly match the loaded CSS family, whether that's a Google Fonts family or a self-hosted `@font-face`'s own `font-family` (`globals.css`), or `document.fonts.load()` silently falls back and the canvas renders tofu/incorrect shaping.
6. **All SEO strings flow from `src/config/site.ts`.** Don't hardcode the site name/URL/description elsewhere.
7. **Strict TypeScript stays on.** Don't loosen `tsconfig.json`; fix the types instead.

## Gotchas learned the hard way

- The **inner-shadow trick** in `engine.ts` (`innerShadow()`) draws the glyph mask far off-canvas and lets only its *shadow* land on the tile, then clips with `destination-in`. The `push` offset math is delicate; read the comments before editing.
- `document.fonts.ready` can resolve before a newly selected face is usable at a specific size; that's why `setBlockFont` awaits `ensureFont()` and then forces a fresh rAF.
- Preview DPR is capped at 2 (`MAX_PREVIEW_DPR`) to keep large canvases fast; export uses `EXPORT_SCALE = 3` regardless.
- `state` is mirrored into `stateRef` so the render loop and export handlers always read fresh values without re-binding listeners.
- Clipboard copy (`ClipboardItem`) is not supported in every browser/context; the catch branch must keep showing the "use Download instead" hint.
- Text input is capped at `MAX_TEXT_LENGTH` (2000 chars) as a canvas-DoS guard; keep the cap if you touch text handling.
- Custom sets (`useDebossStudio.ts`) persist to `localStorage` behind a `customSetsLoadedRef` guard: the load effect sets it after reading storage, and the persist effect bails out until it's true. Otherwise the initial empty `customSets` array would overwrite whatever was already saved before the load effect ran. All `localStorage` calls are wrapped in `try/catch` (private browsing, quota, disabled storage all throw).
- One set can be starred as the default (`defaultSetId`, its own `localStorage` key). Its *style* (never any text block; `CustomSet.state` excludes `textBlocks` entirely by design) is applied to `state` inside the SAME load effect that reads `customSets` from storage, synchronously with the load rather than in a later render. This is what avoids a flash of the built-in default before the user's default appears, since the canvas doesn't paint at all until fonts are ready (much slower than a localStorage read). Deleting the default set clears `defaultSetId` too.
- **`layout.tsx` MUST stay `async` and call `await headers()`, even though the value looks unused.** That call is what makes the route render per-request instead of being served as a cached static shell; it's the only way Next's renderer can see `middleware.ts`'s fresh nonce and stamp it onto the scripts it manages. Remove it and every script gets blocked in production (happened twice already: once by never adding it, once by "cleaning up" what looked like dead code).
- **Never add a `nonce` prop to the JSON-LD `<script>` in `layout.tsx`.** It's `type="application/ld+json"`, which browsers don't enforce `script-src` against (inert data, never executed); it doesn't need one, even though `layout.tsx` does read the nonce (see above). A nonce on THIS specific script previously caused a hydration mismatch, because browsers strip a script's `nonce` attribute from the DOM right after insertion, so React's SSR-rendered value can never match what it reads back client-side.
- **There is no API to publish to a specific app (Instagram or otherwise) from a website.** `shareImage` (`useDebossStudio.ts`) hands the exported PNG to the OS share sheet via the Web Share API (`navigator.share({ files })`); the user still picks the app and completes the post themselves. `canShareImage` feature-detects this on mount (mostly true on mobile, false on most desktop browsers) so the Share button in `PreviewStage.tsx` only renders where it can work. The user cancelling the share sheet rejects with `AbortError`; that must stay a silent no-op, not an error hint.
- **`public/sw.js` (the offline service worker) only registers in production** (`ServiceWorkerRegister.tsx` checks `NODE_ENV === "production"`). Registering it in dev would let its cache-first strategy serve stale JS chunks over Fast Refresh's freshly rebuilt ones. Bump `CACHE_VERSION` inside `sw.js` whenever you change its caching strategy, or returning visitors can get stuck on a stale cached shell; the `activate` handler only clears caches whose name doesn't match the current version.
- **The preset-deep-link effect in `useDebossStudio.ts` MUST stay declared textually after the custom-sets/default-set load effect.** Passive effects with `useEffect(fn, [])` commit in declaration order on mount; both effects call `setState` with overlapping keys, and React applies those updater functions in that same order. Declaring the preset effect second is what makes a `?preset=` URL win over a starred default set, not the reverse. It intentionally reads the `initialPresetId` prop once (empty deps, `eslint-disable-next-line`) rather than reacting to later changes: picking a preset after mount goes through `applyPreset`/`setPresetInUrl` instead.
- **Preset deep link canonical/OG URLs are known-broken by an upstream Next.js bug, accepted deliberately.** `resolveAbsoluteUrlWithPathname` (Next 15.5.20, `next/dist/lib/metadata/resolvers/resolve-url.js`) collapses ANY resolved URL whose `pathname` is exactly `/` down to bare `origin`, silently dropping the query string. Since `/?preset=<id>` pages live at the root path, `alternates.canonical` and `openGraph.url` in `app/page.tsx`'s `generateMetadata` both end up pointing at the plain homepage instead of the preset URL, no matter how the value is constructed. Title/description/OG image stay correct; don't spend time trying to "fix" this in our own code, it's not fixable without moving presets to real path segments (a bigger decision the user has explicitly deferred), see `docs/SEO-PLAN.md` Phase 2 item 4 for the full trace. This bug does NOT affect `/gallery/[slug]` pages, since those are real path segments, not query strings.
- **A `GalleryExample` invalidates on more mutators than a `Preset` or `CustomSet` does, because it uniquely includes the full `textBlocks` array.** `useDebossStudio.ts`'s gallery-example mount effect is declared after the preset effect (same "declared later wins" rule as above). Every mutator that already clears `activeCustomSet` also clears `activeExample` and calls `clearExampleFromUrl()` (which strips only `?example=`, leaving an unrelated `?preset=` alone). Every per-block mutator (`updateTextBlock`, `setBlockFont`, `addTextBlock`) routes through a shared `invalidateExample()` helper for this, since editing/adding a block breaks the one thing a `GalleryExample` exists to pin; `setBlockPosition` and `deleteTextBlock` deliberately do NOT, matching the same "position/deletion is orthogonal to the look" exception branding already gets. Don't reuse the blanket `clearDeepLinkFromUrl()` (wipes the whole query string) for mutators that shouldn't invalidate an active preset: font/align/transparency/tint/shadow-colour/aspect changes don't invalidate a preset today, only a slider or the paper swatch does, and that precedent must keep holding for examples vs. presets too.
- **`TextBlock.text` can contain rich-text markup now, but stays a plain `string`.** It may hold a small, fixed, closed tag vocabulary (`<b>`, `<i>`, `<u>`, `<s>` strikethrough, `<uc>` uppercase, `<span style="font-size:Npx">`, nestable, paragraphs still joined by literal `\n`) that only `lib/deboss/richtext.ts`'s serializer ever generates, never arbitrary pasted HTML. A plain untagged string (every `GALLERY_EXAMPLES` entry, the default sample text) is valid as-is, zero migration needed. Never assume a block's `text` is plain; run it through `hasRichRuns`/`stripTags` (`richtext.ts`) before treating it as one, exactly like `MiniPreview.tsx` and `detectTextDirection` call sites now do. Adding another boolean mark later (matching Bold/Italic/Underline/Strikethrough, NOT a value-carrying one like size) means touching all of: `TextRun`/`MeasuredFragment` (`types/deboss.ts`), `hasRichRuns`'s regex + `OpenTag`'s `kind` union + `parseRuns`'s open/close branches + `flush()` + `wrapRun` + `serializeDoc`/`deserializeToDoc` (`richtext.ts`), `tokenizeParagraph` + `buildBlockMask`'s rich-path draw (`engine.ts`), and the toolbar button itself (`RichTextEditor.tsx`); `measureRichLines` only needs a change too if the mark affects glyph WIDTH (uppercase does, via `text-transform`; underline/strikethrough don't, they're drawn lines with no layout effect).
- **Uppercase (`UppercaseMark.ts`, a custom Tiptap mark since core ships none) is display-only and non-destructive, exactly like Bold/Italic, not a one-time text mutation.** The stored text keeps its original typed case; only drawing (`buildBlockMask`: `frag.uppercase ? frag.text.toUpperCase() : frag.text`) and measuring (`measureRichLines`: `span.style.textTransform`) apply the transform, so toggling the mark off restores the exact original casing. `.toUpperCase()` is a harmless no-op on Arabic/Urdu/Devanagari text (no case concept in those scripts); deliberately not gated per-font/script (no existing capability concept to hook into, and a no-op isn't an error worth building around).
- **`engine.ts` has TWO text-layout paths PER BLOCK, gated on `hasRichRuns(block.text)`, and the plain one must never change.** Untagged text (every existing `GALLERY_EXAMPLES` entry, the default text, anyone who never opens the rich-text toolbar) stays on the original `layoutLines`/single-`fillText`-per-line path, byte-identical to before this feature existed, guaranteeing zero pixel drift on existing content. Tagged text instead measures via a hidden, singleton DOM container (`measureRichLines`, same lazy-create-and-reuse pattern as `_measureCtx`/`_noiseTile`) and reads back the browser's own bidi-correct, wrap-correct positions via `getBoundingClientRect`, since canvas has no native mixed-run text layout API and hand-rolling bidi-aware wrapping is exactly the kind of thing that quietly breaks Arabic/Urdu correctness. Don't try to unify the two paths "for simplicity"; the split is the safety net. Two blocks on the same canvas can independently be on either path, e.g. one plain Latin block and one rich-formatted Urdu block together.
- **Line grouping in `measureRichLines` MUST come from `Range.getClientRects()` per paragraph, never from comparing fragments' own `getBoundingClientRect()` to each other.** A single fragment's rect spans its full font ascent/descent; a much larger font on one line can make that box tall enough to spatially reach into a neighbouring line's rect even though the two sit on genuinely separate, non-overlapping CSS line boxes. This shipped as a real overlapping-text bug once (both across paragraphs and within one paragraph's own word-wrap, whenever two lines had a big enough size difference) before switching to per-paragraph `Range` rects, the browser's own authoritative, guaranteed-non-overlapping line boundaries. Individual fragment rects are still fine for x/width; just not for deciding which line a fragment is on.
- **`FontSizeMark.ts` renders its `size` attribute at TRUE value, uncapped, on purpose.** It used to cap the on-screen CSS at `EDITOR_MAX_DISPLAY_PX` (40px) because the old sidebar editor box was small (~92-260px) and a 150px+ word would blow it out; that box is gone (`CanvasTextOverlay.tsx` now sizes the editor to match the canvas exactly), so the cap was removed rather than kept as dead weight. `data-size` (not the inline `style`) is still the canonical attribute `parseHTML` reads back from, so copy/paste within/into the editor keeps round-tripping correctly; don't remove it as "redundant."
- **`letterSpacing`/`lineHeightFactor` (`TextBlock`, per block) must be applied identically on the measuring side and the drawing side, in both engine paths.** `layoutLines`' `measureCtx` and `measureRichLines`' hidden container both set `letterSpacing` before measuring; `buildBlockMask` sets the same `ctx.letterSpacing` before every `fillText` call (plain and rich), reading that same block's own value. If these ever drift apart, wrapping decisions (made during measurement) stop matching what's actually drawn, i.e. text overflows or wraps at the wrong point. `lineHeightFactor` replaced the old fixed `LINE_FACTOR` constant everywhere except `DEFAULT_TEXT_BLOCK.lineHeightFactor`'s own initial value (still set to `LINE_FACTOR`, so a default/unmodified block renders identically to before this control existed).
- **A style boundary landing mid-word still breaks Arabic/Urdu letter-joining, and no engine change can fix that.** Contextual scripts shape a word's glyphs within a single `fillText` call; splitting a word across two calls (because bold starts partway through it, say) shapes each half in isolation, visibly disconnecting the letterforms at the cut. This is a hard Canvas2D limitation, not a bug in `measureRichLines`. The accepted mitigation, not a workaround to remove: `RichTextEditor.tsx`'s `snapSelectionToWordBoundaries` widens a partial-word selection out to the nearest whitespace before applying any mark, for fonts in `CURSIVE_SCRIPT_FONTS` (`constants.ts`) specifically.
- **`FONT_CAPABILITIES` (`constants.ts`) gates Bold per font, but Italic is deliberately enabled for every font.** Gulzar has no bold weight loaded (Google Fonts URL in `layout.tsx`), so a "bold" Gulzar glyph would only ever be a browser-synthesized ("faux") weight, which visibly merges Gulzar's letter joins; Bold stays gated on a real loaded face for that reason. Italic used to be gated the same way (only Playfair Display has a real italic face; every other font would render a browser-synthesized oblique slant), but that gate was deliberately removed at the user's request so the Italic toolbar button and Ctrl+I work on every font, faux slant included. If you add a font, add its real bold capability here; italic should stay `true` unless a future product decision reverses this again.
- **Self-hosted fonts (`public/fonts/`, e.g. Jameel Noori Nastaleeq + its Kasheeda variant) follow the SAME wiring as a Google Fonts entry, just swapping one step.** `globals.css` has a dedicated "Self-hosted fonts" section right after `:root`, one `@font-face` block per file, each with its own `font-family` name (must match `FontFamily` exactly, per the direction-detection gotcha above); no CSP change is needed since same-origin `/public` assets are already covered by `middleware.ts`'s `font-src 'self'`. Everything else (`types/deboss.ts`'s `FontFamily` union, `constants.ts`'s `FONT_OPTIONS`/`FONT_CAPABILITIES`/`CURSIVE_SCRIPT_FONTS`, the preload list in `useDebossStudio.ts`, both font-family fallback stacks in `globals.css` and `RichTextEditor.tsx`) is identical to adding a Google Fonts entry; only skip the `<link>` URL in `app/layout.tsx`. Both current self-hosted fonts are single-weight files (no separate bold face), so `FONT_CAPABILITIES` sets `bold: false` for them, same reasoning as Gulzar; both are Nastaliq (cursive/contextual-joining), so both are also in `CURSIVE_SCRIPT_FONTS`.
- **`RichTextEditor.tsx` is loaded via `next/dynamic(..., { ssr: false })` from `CanvasTextOverlay.tsx`, mounted whenever a block is SELECTED, not only while actively editing.** It backs the formatting toolbar in both sub-states (see below), so it has to exist before the user ever enters character-cursor mode. Tiptap/ProseMirror are a meaningful chunk of JS; code-splitting them out keeps the bytes off the page's tracked First Load JS (`docs/SEO-PLAN.md`'s "keep it lean" guardrail), and mounting on first SELECT (rather than unconditionally on first paint, like the old sidebar box did) still means the chunk isn't fetched until the user's first click on a block. There's no `loading` fallback: a blank instant while the chunk fetches is an acceptable trade for a deliberate interaction, unlike a fallback that would need to be usable itself.
- **`RichTextEditor.tsx` reloads its content on an explicit `textRevision` counter (`useDebossStudio.ts`), never on the block's `text` directly.** Watching the block's own `text` would fight the user's own typing, since the editor's own `onUpdate → updateTextBlock(id, { text })` round trip would immediately trigger a reload of what it just emitted. `textRevision` is bumped only by mutators that overwrite text from OUTSIDE the editor (currently: the gallery-example deep-link effect, which replaces the whole `textBlocks` array); it must NOT be bumped by `updateTextBlock` itself.
- **`src/lib/blog/posts.ts` (the MDX blog loader) is Node-`fs`-based and server-only.** It reads `content/blog/*.mdx` off disk at request/build time; never import it from a `"use client"` component, and never move it under `src/lib/deboss/` (that tree stays framework-free and touches `document` only lazily, per hard rule #2 — `fs` is a different, stronger constraint again). `src/app/blog/page.tsx` and `src/app/blog/[slug]/page.tsx` are both server components that call it directly; the only client island on either page is `GalleryPreview` for an optional `coverExampleSlug` cover.
- **A blog post's `coverExampleSlug` (frontmatter) reuses an existing `GALLERY_EXAMPLES` slug, not a separate blog-only image.** Posts get a real engine-rendered cover this way instead of a static asset; a post that omits it (or references an unknown slug) simply renders without a cover, no error. Keep blog post titles Latin/English (every topic named in `docs/SEO-PLAN.md` already is): `src/app/blog/[slug]/opengraph-image.tsx` uses the same Satori text renderer as the gallery's, which crashes the production build on non-Latin script for the same documented reason (see that file's own comment).
- **The branding watermark (`state.brandingText/X/Y`) is now pushed through the SAME glyph-mask/inner-shadow engraving pipeline as real text blocks, not a flat `fillText` pass.** `drawBranding` (`engine.ts`) synthesizes a throwaway single-line `TextBlock` (`align: "center"`, `textAnchorX/Y = brandingX/Y`) and a minimal `Layout`, then calls `buildBlockMask` + the shared `compositeEngravedGlyph` helper (also called by `drawScene`'s per-block loop, extracted specifically so branding and real blocks composite identically, no duplicated recess/tint/shadow/highlight logic). For a center-aligned block this math reduces to `tx = textAnchorX*logicalW`/`startY = textAnchorY*logicalH`, bytewise identical positioning to the old flat pass's `brandingX*pxW`/`brandingY*pxH`, so this was a pure rendering-technique change, not a repositioning one. Drawn last inside `drawScene`, unconditionally after the per-block loop, so preview/export stay pixel-identical for free (hard rule #1) and a document can carry only a watermark with zero text blocks. Its "fill colour" is no longer a separate paper-aware flat colour at all (that whole mechanism, `getBrandingFill`/`BRANDING_FILL_ON_LIGHT_PAPER`/`BRANDING_FILL_ON_DARK_PAPER`, was removed): like every other block, it stays colourless and reads purely from the shared shadow/highlight/tint, which already handles the "Black" paper tone correctly. `resolveBrandingFontSize` (`engine.ts`) is the ONE formula shared by drawing AND by `BrandingHandle.tsx`'s drag hit-box/clamping math (via `measureBrandingBox`); if these two ever compute the font size differently, the draggable area silently drifts from what's actually drawn, the same "measuring and drawing must match" principle already documented for `letterSpacing`/`lineHeightFactor`. Position is stored as normalized (0-1) coordinates of the text's CENTER, not raw px, so it stays stable across preview DPR, `EXPORT_SCALE`, and aspect/resize changes. `BrandingHandle.tsx`'s hover/drag selection ring is a light-with-dark-halo `box-shadow`, not a single flat colour, since a plain muted-accent border still washes out on dark paper (this one's unrelated to the text-colour mechanism above, purely the drag handle's own UI affordance).
- **Branding's font/size auto-track `textBlocks[0]` by default (symmetric with the main text for free, zero sync code), but are independently overridable for branding ONLY.** `state.brandingFont`/`brandingFontSize` are `FontFamily | null`/`number | null`; `null` (the default) means "derive live from `textBlocks[0]`," resolved fresh on every render via `resolveBrandingFont`/`resolveBrandingFontSize` (`engine.ts`) rather than copied once, so editing the main block's font/size instantly updates an un-overridden branding watermark with no explicit sync. `resolveBrandingFontSize` derives the auto value as `textBlocks[0].fontSize * BRANDING_DEFAULT_SIZE_RATIO` (stays a visibly smaller watermark, not the same scale as the main text), clamped to `[BRANDING_FONT_SIZE_MIN, BRANDING_FONT_SIZE_MAX]`; the same clamp applies to a manual override. `ControlPanel.tsx`'s Branding Font/Size controls (shown only once `brandingText` is non-empty) always display the RESOLVED value via these two functions, so they read correctly whether auto-tracking or overridden. `useDebossStudio.ts`'s `setBrandingFont`/`setBrandingFontSize` follow the SAME "branding is orthogonal to the look" exception already established for `setBrandingText`/`setBrandingPosition` (no preset/set/example invalidation, no deep-link URL touch); both new fields are also excluded from `CustomSet` (`types/deboss.ts`'s `Omit`), same reasoning as `brandingText/X/Y`, so applying a saved Set never resets an explicit branding override.
- **Branding TEXT persists across sessions via its own `localStorage` key (`BRANDING_TEXT_STORAGE_KEY`), but branding POSITION does not.** A handle is a fixed personal identity (like the starred default set's *style*), not per-design content like a text block's own text; position, by contrast, lives in `DebossState` like every other document-level field and resets to `DEFAULT_STATE`'s default corner on a fresh document. Both are excluded from `CustomSet`/`toSetSnapshot` (`constants.ts`) — a Set is a saved look, not a personal signature. `setBrandingText`/`setBrandingPosition` (`useDebossStudio.ts`) deliberately do NOT clear `activePreset`/`activeCustomSet`/`activeExample` or touch the deep-link URL, the same exception already granted to per-block position, since branding is orthogonal to "the look."
- **`MiniPreview.tsx` explicitly sets `brandingText: ""` in its `miniState` override.** The 76×76px mobile-sheet swatch already reduces the primary block's text to a single glyph for the same reason: a watermark would be meaningless clutter at that size.
- **There is no sidebar text box. Text lives entirely as `state.textBlocks: TextBlock[]`, each edited in place on the canvas** (`CanvasTextOverlay.tsx`, rendered inside `PreviewStage.tsx`'s `.stage-inner`), not in `ControlPanel.tsx` (which only edits the *style* of whichever block is selected). Clicking a block is a Canva-style TWO-STEP gesture, not one: a click on an UNSELECTED block only selects it (bounding box + delete badge, `.canvas-text-hit.is-selected`, the debossed canvas render stays fully visible); a click on an ALREADY-selected block is what enters character-cursor editing (mounts the flat `RichTextEditor.tsx` overlay, pixel-matched to what `buildBlockMask` draws, and suppresses that block's debossed render). Clicking a genuinely empty area of the canvas creates a NEW block there (`addTextBlock`) and jumps straight to editing (deliberately bypasses the two-step gesture, since there's nothing to select-then-edit); clicking outside all blocks (or Escape) fully deselects, unmounting everything, and the canvas shows the real debossed render again. A keyboard-focusable "Edit text" button in `PreviewStage.tsx`'s `.stage-bar` also bypasses the two-step gesture, jumping straight to editing the selected (or first) block, since a canvas has no native text/cursor semantics for assistive tech.
- **While a block is being edited, the canvas SKIPS drawing THAT block's debossed render, so only its flat overlay is visible, not both stacked on top of each other; every other block keeps rendering normally.** `drawScene` (`engine.ts`) takes a `suppressBlockId: string | null` parameter (default `null`); `useDebossStudio.ts`'s render loop passes `editingBlockIdRef.current` (a ref mirroring the `editingBlockId` state the hook owns) so it names exactly one block id at a time: whichever block is focused for editing in the live preview canvas. Paper, every OTHER block's recess-floor/tint/shadow/highlight layers, and the branding watermark (`drawBranding`) all still draw unconditionally, same as always. `buildExportCanvas`, `MiniPreview.tsx`, and `GalleryPreview.tsx` never pass this argument, so it's always `null` there — the committed/exported render is completely unaffected by live editing state, preserving hard rule #1 (same `drawScene` function, same code path; the parameter is explicit and every non-live-preview caller defaults it away). Toggling `editingBlockId` doesn't touch `DebossState`, so it's its own dependency on the render-scheduling effect (alongside `state`) — without that, entering/exiting edit mode wouldn't trigger the suppress/restore repaint.
- **Each text block's position (`TextBlock.textAnchorX/Y`) is an ADDITIVE offset, not a redefinition of layout, and is entirely independent per block.** `buildBlockMask` computes `dx = (textAnchorX - 0.5) * layout.logicalW` / `dy = (textAnchorY - 0.5) * layout.logicalH` once per block, then adds it to whatever `tx`/`startY` (plain path) or fragment `x`/`y` (rich path) that block's own `align`/wrapping would already have produced. At the default `(0.5, 0.5)` this is `(0, 0)`: a single block at its default anchor renders byte-identical to before this feature existed (every `GALLERY_EXAMPLES` entry, every preset, the default document). Don't be tempted to "simplify" by redefining what `align` or the wrap width mean when dragging is involved; the whole point of the additive model is that alignment/wrapping logic never has to know positioning exists, per block.
- **`align` only changes how a block's text justifies WITHIN its own bounding box, never where that box sits.** `buildBlockMask`'s plain-path tx formula for `align === "left"`/`"right"` anchors at `logicalW/2 + dx`, the SAME point `"center"` always used, offset by the block's own measured width (`measureBlockBox`) rather than the canvas's `PAD_X`/`logicalW - PAD_X` margins; `measureRichLines` applies an equivalent uniform shift to every fragment's `x` after measuring, so the rich-text path matches. Before this, switching a SHORT block's align moved it all the way to a canvas edge instead of just re-justifying its text in place, since the old formula treated the whole canvas width (minus padding) as the alignment reference rather than the block's own content width; this shipped as a real bug once, reported as the block itself shifting when clicking Left/Center/Right in the toolbar. `computeContentBox` (`CanvasTextOverlay.tsx`) mirrors this exactly (`left` is now unconditionally `logicalW/2 + dx - width/2` for every align, no more per-align branch), and `BlockOverlay`'s drag math (`baseCenterXNorm`) simplifies to a constant `0.5` for the same reason: the block's own box center is always the same anchor point regardless of align now, so dragging a left/right-aligned block no longer needs align-specific math either. `computeEditBox` (the WYSIWYG typing container) is deliberately NOT part of this: it represents the full wrap column, not the block's own hugging box, so actively typing and clicking align without deselecting first can still show a brief mismatch versus the committed canvas render until you click away; the common select-then-align flow (which renders via the canvas, not the edit overlay) is unaffected.
- **Letter-spacing/line-height live in a small labeled popover (`.rich-text-spacing-panel`, `RichTextEditor.tsx`), not two bare `-`/value/`+` steppers.** The original steppers had no visible label at all (only a `title` tooltip), which was reported as confusing; the popover reuses the sidebar's own `.slider`/`.slider-head`/`input[type="range"]` markup (`globals.css`, styled globally, not scoped to `ControlPanel.tsx`) so both fields show a real label and live value, matching Canva's own spacing panel. Rendered as a normal DOM child of the toolbar (inside `.rich-text-spacing-wrap`), not a separate portal: the toolbar is already portaled to `document.body` with no overflow clipping, and staying a descendant means `CanvasTextOverlay.tsx`'s existing `.closest(".rich-text-toolbar")` outside-pointerdown exception already covers dismissing it correctly, no new special-casing needed there. Dismissed via its own `pointerdown`-outside listener scoped to `spacingWrapRef`, independent of the toolbar's own dismiss logic.
- **Every toolbar control's tooltip is a CSS-only `[data-tooltip]::after` bubble (`globals.css`), not the native `title` attribute.** `title`'s OS-styled, slow-to-appear tooltip was replaced outright (not layered on top of the custom one, which would show both) once every control already had `aria-label` covering accessibility on its own. Add `data-tooltip="..."` (not `title`) to any new toolbar control; the CSS applies uniformly with no extra markup or JS.
- **On mobile, the docked toolbar (`.rich-text-toolbar.is-docked`) is a single horizontally-scrollable row (Canva-style), not a wrapping multi-line bar.** Every direct child needs its own `flex-shrink: 0` (already set alongside each control's own rule: `.rich-text-btn`, `.rich-text-size-stepper`, `.rich-text-spacing-wrap`, `.rich-text-toolbar-divider`) or it would get squished instead of the row simply scrolling once content overflows. The letter-spacing/line-height popover (`.rich-text-spacing-panel`) also switches to a full-width bar flush above the (bottom-docked) toolbar at this breakpoint, positioned via a `--spacing-panel-offset` CSS custom property that `RichTextEditor.tsx` sets from the toolbar's own live `getBoundingClientRect()` (`spacingPanelOffset` state): this can't be a fixed CSS offset since safe-area insets and touch-target sizing both affect the docked bar's actual height. Docked buttons ALSO gain a small text label under their icon (`.rich-text-btn-label`, hidden by `display:none` outside `.is-docked`) for the same "icon alone is unclear" reason as the tooltips below; only the icon-only buttons (Bold/Italic/Underline/Align/Spacing) get one, since the font-size stepper already shows its own live number inline.
- **`.rich-text-size-stepper` has NO `overflow: hidden` (removed deliberately).** It used to, to clip its -/+ buttons' square hover-highlight to the pill's rounded shape, but that also silently clipped their `[data-tooltip]` bubbles (positioned outside the stepper's own box), reported as "tooltip not showing on the font-size stepper." Fixed the same visual clipping a different way instead: `.rich-text-size-btn:first-child`/`:last-child` carry their own matching corner `border-radius` directly, so the pill shape holds without an ancestor that clips anything positioned outside its bounds. If you add another pill-shaped control with an ancestor `overflow: hidden` purely for corner-rounding, prefer this per-child-radius pattern over overflow clipping, since overflow clipping silently breaks ANY absolutely/fixed-positioned descendant that's meant to render outside the box (tooltips, popovers, etc.), not just this one case.
- **`measureBlockBox` (`engine.ts`) must use the exact same font/letterSpacing/direction setup as `layoutLines`/`measureRichLines` FOR THAT SAME BLOCK, and `CanvasTextOverlay.tsx` must derive each block's editing/hit-test boxes from it, not from its own guesses.** Same "measuring and drawing must match" principle already documented for `letterSpacing`/`lineHeightFactor` and for the branding watermark; if this drifts, the draggable/clickable region silently stops matching what's actually drawn. Two DIFFERENT boxes are computed per block on purpose: `computeEditBox` always spans the full wrap width (`logicalW - 2*PAD_X`, shifted by `dx`) so typing/wrapping matches the canvas regardless of drag position, while `computeContentBox` hugs that block's actual measured content (used for the idle/selected hit-region AND for drag clamping) so short/centered text has real room to move instead of being confined to the wrap column's own narrow padding margin.
- **`computeLayout(state, logicalW)` sizes the canvas from `state.textBlocks[0]` ALONE when `aspect === "auto"`, never from a bounding box of every block.** Fitting all blocks would be circular (canvas size would depend on block positions, which are themselves fractions of canvas size) and would make the canvas visibly jump as a dragged block nears an edge. This is also what keeps a migrated single-block document byte-identical: with one block, "size from block[0]" is the only sizing rule that ever existed. Additional blocks are placed freely within whatever size that produces and clamped to stay inside it, same as the branding watermark already was.
- **Canva-style center alignment guides (`CENTER_SNAP_THRESHOLD_PX`, `constants.ts`) live in `useDebossStudio.ts`'s `activeGuides` state, not inside `CanvasTextOverlay.tsx`/`BrandingHandle.tsx` themselves, because the two are independent sibling drag sources under `PreviewStage.tsx` and only one can be dragging at a time.** Both `BlockOverlay`'s `handlePointerMove` and `BrandingHandle`'s `handlePointerMove` snap their own normalized center coordinate to exactly `0.5` (before any align-aware offset math runs, in the block case) whenever within `CENTER_SNAP_THRESHOLD_PX` logical px of true center, and call `setActiveGuides`; both `handlePointerUp`/`endDrag` unconditionally clear it so a guide never gets stuck visible after release. `CanvasTextOverlay`'s own render reads `activeGuides` and draws the two `.canvas-align-guide` divs using the SAME `canvasBox` state it already computes for `.canvas-text-background`, no separate measurement needed. This is canvas-center snapping only, deliberately not snapping to other blocks' edges/centers or to canvas edges, that would be a materially bigger feature.
- **The delete button inside a selected block's hit-region must stop propagation on `pointerdown`, `pointerup`, AND `pointercancel` together, not just `pointerdown`.** This shipped as a real bug once: with only `pointerdown` stopped, the button's `pointerup` still bubbled natively to the parent `.canvas-text-hit`'s own `onPointerUp` handler, which (seeing no drag in progress) fired `setEditingBlockId(id)` for the very block about to be deleted; React's resulting re-render swapped the button out of the DOM for the edit container before the browser could ever synthesize a `click` event at that point, so `deleteTextBlock` silently never fired and the block survived, stuck in a zombie edit-mode state. Any future control nested inside a `.canvas-text-hit` needs all three pointer events stopped, matching this precedent.
- **The full-canvas `.canvas-text-background` click-to-create-a-block layer must distinguish "this click's only job was dismissing an open editor" from "this click means create a new block here."** A plain click on empty canvas while a block is being edited would otherwise fire BOTH the editing block's own outside-pointerdown dismiss listener AND the background's create-a-block handler from the same physical gesture. `handleBackgroundPointerDown` captures `wasEditing = editingBlockId !== null` at `pointerdown` time (before the dismiss listener can clear it), and `handleBackgroundPointerUp` skips `addTextBlock` when `wasEditing` was true. Don't remove this capture-before-clear ordering; it relies on the child block's own outside-pointerdown listener running before this background layer's `pointerup`.
- **Editing vs. dragging a block are mutually exclusive per gesture, and clicking IS now a separate "select" step (drag still bypasses it).** `BlockOverlay`'s idle/selected hit-region tracks pointer movement from `onPointerDown`; if it exceeds `DRAG_THRESHOLD_PX` before release, the gesture becomes a drag (`setBlockPosition`, also selecting the block) and edit mode is suppressed regardless of prior selection state. Otherwise, on release: `if (isSelected) setEditingBlockId(...) else setSelectedBlockId(...)` — an unselected block's click only selects it, an already-selected block's click enters editing (see the "two-step gesture" gotcha above). Once editing, that block's hit-region isn't rendered at all (replaced by the edit container), so Tiptap's own text-selection pointer handling never conflicts with block-repositioning — repositioning again requires exiting edit mode first (click outside/Escape, which now fully deselects rather than just exiting typing).
- **DOM (contentEditable) and Canvas 2D (`fillText`) text metrics are not always pixel-identical, and this shows up most when the active font doesn't cover the typed script.** E.g. typing Latin text while a Nastaliq/Naskh font is selected: canvas's `ctx.font` fallback and the DOM overlay's declared CSS `font-family` fallback stack can resolve to genuinely different substituted fonts, producing a visible offset between the flat editing overlay and the debossed result underneath. This is a disclosed, accepted limitation (the same one already true of `measureRichLines`' DOM-based approach), not a bug to chase: it only appears for the uncommon case of a script the active font wasn't designed for. Verified to align tightly whenever the font actually covers what's typed.
- **`isPaperDark` (`engine.ts`, exported) is the shared luminance check for anything drawn or overlaid on the paper that needs to stay legible on the "Black" `PAPER_TONES` entry.** The branding watermark's fill and the in-place editor's plain preview text colour (`CanvasTextOverlay.tsx`'s `is-dark-paper` class) both call it rather than each hardcoding their own threshold; add new paper-aware UI through this function too, don't duplicate the luminance formula.
- **`RichTextEditor.tsx` now derives font-size/line-height/letter-spacing/text-align from props (`baseSize`, `lineHeightFactor`, `letterSpacing`, `align`), sourced from whichever `TextBlock` is being edited and applied imperatively via `root.style.*` in the same effect that already sets `font-family`/`dir`.** These used to be fixed CSS values in `globals.css` (a decorative ~1.35rem/2.1 line-height, since the old sidebar box never needed to pixel-match the canvas); now that this editor IS the canvas rendering while active, they must track that block's own fields exactly the way `buildBlockMask` reads them, or typed text visibly doesn't match its own font size once committed.
- **The floating formatting toolbar (`RichTextEditor.tsx`'s `.rich-text-toolbar`) is portaled to `document.body` via `createPortal`, NOT rendered as a normal DOM descendant of the edit block.** It used to be nested inside `.canvas-text-overlay` (positioned `absolute`, `bottom: 100%`), which is itself inside `.stage-inner` (`overflow: hidden`): a block near any canvas edge pushed the toolbar partly past that boundary and it got silently clipped, a real bug caught during verification. The fix has two parts that both matter: (1) portaling out of `.stage-inner` entirely removes the clipping ancestor, and being a `position: fixed` body-level element also makes it paint above the sidebar/mobile sheet for free (a positioned element with a stacking context always paints after static-positioned siblings, regardless of DOM order); (2) `recomputeToolbarPosition` measures the CANVAS's own live box (via the `canvasRef` prop, `getBoundingClientRect()`, not a character selection or the selected block's own box) and the toolbar's own rendered size (`toolbarRef`), and docks it just above the canvas, centered horizontally, clamped into the viewport if there's no room above, all computed in JS since CSS alone can't express "clamp near a viewport edge" once the element is no longer a DOM descendant of what it's anchored to. This is a deliberate Canva-style redesign (a persistent bar in one stable spot, not floating near whichever block happens to be selected): anchoring to the selected block instead used to let the toolbar land overlapping the site's own (non-sticky) navbar whenever a block was near the top of the canvas, a real bug reported once. Anchoring to the canvas itself means the toolbar never moves when selection changes and can't collide with the navbar, since its position no longer depends on block position at all. `.rich-text-toolbar`'s CSS lost its `position: absolute; bottom: 100%; left: 0` (now `position: fixed` with `top`/`left` set inline from JS, skipped entirely on mobile, see below) and gained `z-index: 46` (above the mobile section-sheet (40/41) and the mini-preview swatch (45), below `ConfirmDialog`'s modal overlay (50)). If you add another block-anchored floating UI element, this portal-plus-measured-position pattern is the one to reuse, not nesting it inside the clipped overlay again.
- **The toolbar is a BLOCK-SELECTION toolbar (Canva-style), not a character-selection toolbar.** It shows for as long as `RichTextEditor.tsx` is mounted at all, i.e. for as long as its block is `selectedBlockId`, in EITHER sub-state (selected-only or actively editing) — there's no separate visibility state inside the component any more, mounting IS showing. This is a deliberate reversal of an earlier design (a Google Docs/Medium-style toolbar gated on a non-empty *character* selection, requiring drag-select or Ctrl+A even after clicking into a block) that this same request replaced. Formatting scope differs by sub-state: **selected-only** — the mount effect calls `editor.commands.selectAll()` (no `.focus()`, see below) so every toolbar action applies to the block's WHOLE text, matching "just selecting the block is enough," no character selection needed; **editing** — completely unchanged from before, a collapsed cursor formats future typed text, a drag-selected range formats just that range. Don't conflate the two or "simplify" them into one behavior; the split is intentional and user-confirmed.
- **Every toolbar command chain goes through `beginChain(editor)`, never a bare `editor.chain()`, and NEVER calls `.focus()` while merely selected (not editing).** This is load-bearing, not cosmetic: `CanvasTextOverlay.tsx`'s block-delete keydown listener (Delete/Backspace while selected-not-editing) listens on `window`, not on a specific element, and does not check which element currently holds DOM focus. If the invisible, selected-only-mounted Tiptap instance ever actually gained real DOM focus, ProseMirror's own keymap would intercept Backspace at the contentEditable *before* it ever bubbles to `window`, corrupting the hidden doc instead of (or in addition to) deleting the whole block. `beginChain` is the one guard against this: `(ed) => isEditing ? ed.chain().focus() : ed.chain()`. The underlying commands (`toggleBold`/`toggleItalic`/`toggleUnderline`/`setFontSize`) apply to `editor.state.selection` regardless of DOM focus, so skipping `.focus()` while selected-only costs nothing functionally.
- **`BlockOverlay`'s RichTextEditor wrapper mounts whenever `isSelected` (both sub-states), staying INVISIBLE (`opacity: 0; pointer-events: none`, never `display: none`) until `isEditing`.** `display: none` risks breaking ProseMirror's internal selection/measurement machinery on a node the browser treats as not rendered; `opacity: 0` keeps it a real laid-out DOM node the whole time. The idle/selected hit-region (`.canvas-text-hit`, outline + delete badge) renders as a SIBLING whenever `!isEditing`, so while merely selected, both exist simultaneously: the invisible editor backs the toolbar, the hit-region handles click/drag/delete, and the debossed canvas render (unsuppressed, since suppression is keyed to `editingBlockId` specifically, not `selectedBlockId`) is what the user actually sees.
- **Both of `BlockOverlay`'s top-level children (the hit-region and the RichTextEditor wrapper) sit inside a single outer `<div style={{ display: "contents" }}>` that `containerRef` points to, not on either child individually.** `display: contents` makes the wrapper contribute no box of its own (children still position absolutely against `.stage-inner` exactly as if it weren't there) while still existing as a real DOM node for `.contains()` checks. This shipped as a real bug once: with `containerRef` on only the RichTextEditor wrapper, a SECOND click on a block's own hit-region (to go from selected-only into editing) landed on a sibling `containerRef` didn't contain, so the outside-pointerdown dismiss listener read it as an outside click and deselected on pointerdown before the click could ever register — the block appeared to just get "stuck" selected, never entering edit mode. Keep both children under this one wrapper; don't split them back into true top-level siblings.
- **`BlockOverlay`'s outside-pointerdown dismiss listener uses functional updaters (`setSelectedBlockId((cur) => cur === block.id ? null : cur)`), never a plain `setSelectedBlockId(null)`.** Selected-not-editing is the common state now (reached by every first click), so tapping a DIFFERENT block B routinely fires both B's own select handler and block A's outside-pointerdown listener in the same tick, with no guaranteed ordering between a raw `document.addEventListener` callback and React's synthetic event handler. A plain `null` write from A could land after B's own `setSelectedBlockId(B.id)` and clobber it; the functional form only clears when the id still matches, making it order-independent (same pattern `deleteTextBlock` already uses in `useDebossStudio.ts`). Escape's handler doesn't need this (no concurrent competing writer), so it uses plain `null`.
- **On mobile (`max-width: 880px`, matching `globals.css`'s primary breakpoint), the toolbar docks as a full-width bar at the BOTTOM of the screen instead of floating near the block** (`RichTextEditor.tsx` tracks `isMobileDocked` via `matchMedia`, skips `recomputeToolbarPosition`/the inline `top`/`left` style, and adds an `.is-docked` class that CSS positions via `bottom`, not `top`, for easy thumb reach). `ControlPanel.tsx`'s mobile-only section menu (Presets/Engraving/Type & Paper bottom sheets) deselects any active block (`setSelectedBlockId(null)`/`setEditingBlockId(null)`) before opening a sheet, specifically so the docked toolbar never has to compete with the `.mini-preview` swatch (top-anchored) or a bottom sheet (also bottom-anchored) for the same strip of screen; the desktop accordion's own `toggleSection` is untouched since desktop has no such overlap risk. The letter-spacing/line-height popover (`.rich-text-spacing-panel`) opens UPWARD, flush above the bottom-docked bar, via `spacingPanelOffset` (`RichTextEditor.tsx`, the live distance from the viewport's bottom edge to the toolbar's own top edge) rather than the downward-opening layout it'd need if the bar were still top-docked.
- **`ControlPanel.tsx`'s Type & Paper section exposes ONLY the Font select as a per-block control; Alignment/Letter-spacing/Line-height controls live in the floating per-block toolbar (`RichTextEditor.tsx`) instead, not the sidebar.** They were removed from the sidebar once (to declutter a section that was mostly greyed out) and later reintroduced, but relocated rather than restored in place: `RichTextEditor.tsx`'s toolbar gained 3 alignment buttons (`AlignLeft`/`AlignCenter`/`AlignRight`, right after Underline) and two more pill steppers (letter-spacing, line-height, after the font-size stepper), all writing through `updateTextBlock` (`CanvasTextOverlay.tsx`'s `BlockOverlay`, which already exists specifically to back "text, alignment, letter spacing, and line height" per its own doc comment) rather than any new state. The new letter-spacing/line-height steppers reuse `TYPE_SLIDER_DEFS`'s existing min/max/step values (`constants.ts`) instead of hardcoding new ones. Deliberately NOT built by refactoring the existing font-size stepper to share code: that one is tightly coupled to Tiptap's `runFormatting`/`beginChain`/mark-selection commands (a fundamentally different commit path, since font size is a per-run Tiptap mark, not a `TextBlock`-level field like these three), so a separate `ToolbarStepper` component backs only the two new controls, leaving the working, gotcha-documented font-size stepper untouched. Font ALSO no longer requires a block to be selected: `fontTargetBlock = selectedBlock ?? state.textBlocks[0] ?? null` falls back to the first block, so the picker stays usable (and is never rendered `disabled` with a "select a block" hint, which was removed alongside it) even with nothing selected on canvas, a deliberate divergence from the "always reflects the active object" rule the rest of this section (and `docs/ARCHITECTURE.md`) still describes for anything reintroduced here later.
- **`onPointerDownOutside` in `CanvasTextOverlay.tsx`'s `BlockOverlay` MUST treat a click on `.rich-text-toolbar` as "inside" the editor, even though it's DOM-wise a `document.body` descendant, not a descendant of this block's own edit container.** This shipped as a real bug once the toolbar was portaled: with only `containerRef.current.contains(e.target)` checked, EVERY tap on a formatting button read as an outside click and called `setEditingBlockId(null)` on `pointerdown`, unmounting the whole editor (and the button being pressed) before its `click` handler could ever run — formatting silently never applied, indistinguishable from "the tap did nothing." The fix is a second early-return: `if ((target as HTMLElement).closest?.(".rich-text-toolbar")) return;`. Any other portaled-to-body UI that should count as "part of the editor" for this dismiss check needs the same treatment; DOM containment alone isn't enough once something is portaled.
- **The toolbar buttons preserve the text selection through a tap/click via `onMouseDown={e => e.preventDefault()}` ONLY, deliberately not `onTouchStart` too, despite the bug this fixes being most visible on touch.** Two touchstart approaches were tried and both made things worse: an `onTouchStart` prop is a no-op in React, since React registers its delegated `touchstart` listener as PASSIVE by default (a scroll-performance optimization), so `preventDefault()` inside it silently fails and logs "Unable to preventDefault inside passive event listener invocation" on every tap; forcing a real native `{ passive: false }` touchstart listener DOES prevent the default, but that also cancels the browser's synthesized `mousedown`/`mouseup`/`click` compatibility events for that same tap, so the button's `onClick` (where the formatting command actually runs) never fires at all, verified with Playwright's touch emulation. Touch browsers still synthesize a `mousedown` after every tap release for compatibility (unless touchstart's own default was prevented, the case that breaks it), and that synthesized mousedown is what actually carries the focus-stealing default action (blurring the contentEditable, collapsing/clearing its selection) this needs to cancel — on mouse AND touch alike, so `onMouseDown` alone is both necessary and sufficient. Don't "complete the pair" by adding `onTouchStart` back.
- **The font-size stepper's number input does NOT get the `onMouseDown` preventDefault pattern the -/+ buttons and B/I/U buttons get, on purpose.** It must accept real focus to be typeable at all: `preventDefault` on its own mousedown would block focus from ever landing there, meaning the user could never click into it. It's still selection-safe without it: ProseMirror does NOT clear `editor.state.selection` on a mere DOM blur (only an explicit transaction does), so the original selected range survives the input stealing focus, and `editor.chain().focus()...` inside `applySize`/`runFormatting` re-selects that exact range in the DOM before the size mark is actually applied, restoring focus to the editor at the same time. Don't "fix" this by adding the same preventDefault pattern here; it would make the input non-interactive. (There used to be an attached preset `<select>` here too, removed as a redundant duplicate of the same number the input already shows; if one comes back, it inherits this same exception, since a native select's mousedown is what opens its dropdown in most browsers.)
- **The size input is a local text draft (`sizeDraft` state), not a value bound straight to the mark's current size, and only re-syncs from it while the input itself doesn't have focus (`document.activeElement !== sizeInputRef.current`).** Syncing unconditionally would fight every keystroke: typing "72" would re-render with the old committed value between each digit. It applies (parses, clamps to `[MIN_SIZE, MAX_SIZE]`, calls `applySize`) on Enter and on blur, not on every keystroke, matching the two explicit commit points this control is designed around; an empty or non-numeric draft on commit reverts to the current size rather than applying anything.
- **The gallery-submission feature ("request to post on gallery") is the app's first-ever outbound network call, and ships deliberately inert until the site owner supplies real config.** `isGallerySubmissionConfigured()` (`src/config/gallery-submission.ts`) checks all 5 `NEXT_PUBLIC_EMAILJS_*`/`NEXT_PUBLIC_GALLERY_SHEET_WEBAPP_URL` env vars against a placeholder sentinel; both entry points gate on it (`RequestPostButton.tsx` renders `null`, `CreateLauncher.tsx` renders `null`), and `GallerySubmissionModal.tsx` ALSO checks it independently and renders a "not set up yet" message instead of a form, so even if a future caller forgets to gate its own launcher, the modal itself never wires up a broken submit. See `docs/GALLERY_SUBMISSION_SETUP.md` for what the owner must configure.
- **There are exactly TWO EmailJS templates, each with a different audience and a different "To Email" wiring; don't add a third without the user's explicit go-ahead (already asked for, then explicitly declined once).** OTP (`emailjsOtpTemplateId`) goes to the SUBMITTER, so its "To Email" field must be set to the dynamic `{{to_email}}` in the EmailJS dashboard (`sendOtpEmail` passes `to_email` in `template_params`, see `emailjs.ts`). Notify (`emailjsNotifyTemplateId`) goes to the OWNER only, so its "To Email" is a FIXED address typed directly into the template, never passed as a parameter; mixing these two wiring styles up is the most common setup mistake (see `docs/GALLERY_SUBMISSION_SETUP.md`). The visitor's only correspondence is the OTP email itself; there is no separate post-verification confirmation sent to them.
- **`{{thumbnail}}` in the Notify EmailJS template is a raw base64 `data:image/png;base64,...` string, not an image by itself.** Used in a Plain Content template it just prints as a huge garbled string; to actually render it, the owner's Notify template must be in EmailJS's HTML/rich editor mode with `<img src="{{thumbnail}}" />`, not the plain-text mode.
- **`submitToSheet` (`sheet.ts`) runs Display Name/Email/Description/Set Name through `sanitizeForSheet` before they're appended as a row.** A value starting with `=`, `+`, `-`, `@`, tab, or carriage return can execute as a spreadsheet formula once it lands in the owner's Sheet (a known CSV/spreadsheet injection class); the sanitizer prefixes a leading apostrophe to force it to stay plain text. Deliberately NOT applied to the EmailJS notification body (`emailjs.ts`), which has no equivalent formula-execution risk. If a new user-controlled string field is ever added to `SubmissionPayload`, route it through this same sanitizer before it reaches `submitToSheet`'s body.
- **OTP attempts are enforced in TWO places, not just the displayed error text.** `verifyAndSubmit` (`GallerySubmissionModal.tsx`) early-returns once `attempts >= OTP_MAX_ATTEMPTS`, AND the Verify button's own `disabled` prop checks the same condition; the button-level check alone isn't enough since the surrounding `<form>` could still be submitted directly. `resendOtp` is the only path that resets `attempts` back to 0 (a fresh code, fresh attempt budget).
- **`GallerySubmissionModal`'s in-modal `GalleryPreview` can render a MUCH taller canvas than it looks like it should, because the submitted `TextBlock`s carry a `fontSize` tuned for the real studio canvas (often 600-1200px wide) but this preview renders at a fixed, much narrower `SUBMISSION_PREVIEW_LOGICAL_W` (320px).** At that width the same text wraps into far more lines, and `computeLayout`'s `"auto"` aspect mode has no notion of "this is a small preview," only its own blanket `MAX_LOGICAL_H` clamp (1100 logical px), so the canvas can legitimately come back over 1000px tall, blowing out the whole modal's layout (shipped as a real bug once, reported as "the modal opens behind the preview"). The fix is CSS-only: `.gallery-submit-modal .gallery-preview` (`globals.css`) sets an explicit `max-height: 320px`, which is what finally gives the shared `.gallery-preview` class's existing `overflow: hidden` (it has none of its own height cap, so it normally just grows to fit whatever canvas lands inside it) something to actually clip. This crops excess height rather than scaling the design down; don't "fix" this by touching `computeLayout`/`GalleryPreview.tsx`, both are shared with the real gallery pages where this behavior is correct and expected.
- **`GallerySubmissionModal.tsx` and `SetPickerModal.tsx` are both portaled to `document.body` via `createPortal`, NOT rendered as a normal DOM descendant of their launchers (`RequestPostButton.tsx`, `CreateLauncher.tsx`).** `.panel` (the sidebar, `globals.css`) is `position: sticky`, which unconditionally establishes its own stacking context (true of `position: sticky` even with no explicit `z-index`, unlike plain `position: relative`); a `position: fixed` modal nested inside it has its paint order trapped within that LOCAL stacking context instead of competing at the page root, so no matter how high the modal's own `z-index` is, it renders BEHIND `.stage`/`PreviewStage`'s real canvas, a DOM sibling of `.panel` with no `z-index` of its own that simply paints later because it comes after `.panel` in the layout. This shipped as a real bug once, reported as "the modal opens behind the preview." Portaling out of `.panel` entirely removes the trapping ancestor; this is the same fix already used for `RichTextEditor.tsx`'s floating toolbar (see that gotcha above) for an analogous nesting problem, and the same class of bug likely latent in `ConfirmDialog.tsx` too (not fixed there since it hasn't been reported broken, but don't be surprised if it is).
- **A submission's "set" is a synthesized `DebossState`, never `targetSet.state` alone, because `CustomSet` excludes `textBlocks`/branding entirely (see `CustomSet` in `types/deboss.ts`).** `GallerySubmissionModal.tsx` builds `{ ...DEFAULT_STATE, ...targetSet.state, textBlocks }`, the same merge order `applyCustomSet` already uses in `useDebossStudio.ts`. The two entry points differ ONLY in which `textBlocks` they pass: `RequestPostButton.tsx` (studio-page set-chip) passes the visitor's CURRENT on-canvas `state.textBlocks`; `CreateLauncher.tsx` (navbar, every page, no live canvas) passes `[DEFAULT_TEXT_BLOCK]`. Don't add a third way to source text without updating both call sites' reasoning.
- **The gallery-submission OTP is friction, not fortress, by deliberate user-confirmed design, not an oversight.** `generateOtp()` (`src/lib/gallery-submission/otp.ts`) runs entirely client-side and is compared against browser memory in `GallerySubmissionModal.tsx`; with no backend to keep it secret (this app's hard "no server" rule), a determined visitor could read it out of devtools/network before "verifying." It still serves a real purpose (confirms a reachable email, deters casual bots/typos) and is backstopped by a per-session send cap (`MAX_OTP_SENDS_PER_SESSION`) and a honeypot field, plus the fact that every submission lands in the owner's inbox/spreadsheet for manual review before anything reaches the real gallery. Don't "harden" this with more client-side cleverness; the actual fix would require a backend, which is out of scope by design.

## Style conventions

- Named exports for components (no default exports except Next.js route files, which require them).
- Path alias `@/*` → `src/*`.
- Comments explain *why*, not *what*. The engine is intentionally heavily commented; preserve that.
- Keep components presentational; new interactive logic goes in the hook or a new hook, not in JSX files.
- **Icons are `lucide-react` components, never literal glyph characters** (no `×`, `★`, `+`, etc. as button text). Import only the icons used; size via the `size` prop (14 for compact chip/form controls, 16 for `.btn` actions), and add `aria-hidden="true"` when the button already has an accessible label so the icon isn't announced twice.
